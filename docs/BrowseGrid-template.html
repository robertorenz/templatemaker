BrowseGrid

Draws any ABC browse with Direct2D and DirectWrite instead of the run-time LIST — banding, frozen columns, its own heading, crisp text, totals and per-cell colour — without touching the browse underneath.

ABC · bound at run time, nothing to redistribute · <200 µs a fill · EN/ES

Overview #

The whole idea of this template is in the second half of that sentence.

BrowseGrid creates a REGION exactly on top of the browse's LIST and draws the rows there itself. The LIST goes on filling its queue, counting visible rows and holding the selection — it simply stops being the thing you look at.

It is hidden from Windows, not from Clarion WS_VISIBLE is stripped off the LIST's HWND, so Windows never paints it. HIDE() would not do: that makes ABC decide it has no rows to load. Clearing the style bit leaves PROP:Hide, the queue and the visible-row count untouched. The LIST also keeps the focus, which is why every key an ABC browse has always answered goes on working without a line being written — arrows, PageUp/PageDown, the incremental locator, Insert, Delete, Enter. The region only ever needed the mouse, and a REGION with PROP:IMM gets that with or without focus.

That is why BrowseClass keeps its file, order, filter, range and locator intact. This replaces how the rows look, not how they are obtained — and it is what lets an existing browse carry on working the moment you switch the extension off.

Where what it draws comes from

  • The columns, from the LIST itself at run time, through PROPLIST: widths, headings, pictures and alignment. Whatever you set in the formatter travels across on its own — including a column the user has just moved or resized.
  • The values, from the browse queue, read generically with WHAT(queue, field). Nothing here knows or cares which file is underneath.
  • The conditional colours, from the queue as well. ABC has already evaluated your conditions and left the four colours there; the grid honours them with nothing to configure.
Direct2D and DirectWrite are bound at run time with LoadLibrary, so there is no import library and nothing to redistribute. Both have shipped with Windows since 7. If they were missing, the grid does not start and leaves you the ordinary LIST.

Install & register #

BrowseGrid.tpl  → template\win
d2grid.c      → libsrc\win — the engine, compiled by Clacpp with your app

Setup → Template Registry → Add → BrowseGrid.tpl, then add the extension to a browse procedure and name the LIST it takes over.

d2grid.c has to be where the redirection file can find it The template adds it to the project. If it is only in the template folder, the compile fails on a source file it cannot find rather than on anything to do with the grid.

The two extensions #

BrowseGridGlobal — once per application

Optional. It carries the application-wide defaults, of which the one that matters is the language of the texts the end user sees. Without it, each grid falls back to English.

BrowseGrid — one per browse

The working extension, MULTI, so a window with two browses gets two of them. Each needs its own Object name.

The AppGen prompts stay in English whichever language you pick A programmer reads them; an end user never does.

Settings shared by every browse #

Most of what you configure has nothing to do with which browse it is. That part can be set once, on the global extension, and inherited.

Three groups, each with its own tab on BrowseGridGlobal and its own tick on the browse:

GroupCoversTick on the browse
Heading menuThe nine menu options, the drop-down button, auto-fit and its look-aheadHeading menu tab
LookTypeface, SDAspecto, GDI rendering, weight, wrapping, heights, the eight colours and the eleven variablesLook tab
MouseScrollbars and their style, the browse popup, double-click, wheel, tooltipsMouse tab
Look, Colours and Variables are inherited together, by one tick Variables overrides the other two — a variable name put there wins over the fixed value above it — so inheriting one of the three alone would leave the grid with half of one theme and half of another, and which half won would depend on the field. A theme is one thing or it is nothing.
What is deliberately not inherited LIST columns that also get the click. Those are column numbers belonging to that browse and mean nothing in another one; inheriting them would send the event to the wrong column, which is worse than not sending it.
The global's values are factory defaults until you touch them In particular the drop-down button is off there too, so ticking the menu inheritance without switching it on in the global leaves that browse with no heading menu at all. With the tick set but no global extension in the application, the local settings stand: borrowing from something that is not there cannot switch a menu off.

Columns & Heading menu tabs #

The columns come from the LIST. These two tabs decide what the user may do with them.

The prompts are spread over seven tabs Browse, Columns, Heading menu, Look, Colours, Variables and Mouse. The split is by what things share rather than by size: Heading menu holds filtering and auto-fit together because both hang off the same tick — without the drop-down button there is no menu to put them on — and Colours and Variables come out of Look because they are long flat lists, not typography.

Excel-style drop-down button on every headingoffAdds the filter button to each heading, and with it the whole column menu.
Offer Filter by value… on that menuonSee the warning below.
Browse objectblankBlank is deduced from the queue name: a browse's control, queue and object carry the same number (?Browse:5, Queue:5, BRW5), and no number means the first. Only write it if you renamed the object.
A row of totals along the bottomoffSums every record the browse shows, filter and range included — not the page on screen.
Auto-fit column widths on the heading menuonAdds Auto-fit widths to the menu, which sizes every visible column to the widest of its heading and its values.
Records to look ahead1000How far past the loaded page to read. At 0 no file is touched — only what is already in memory is measured.
Filter by value is the one sequential scan in the template It walks the whole file collecting the distinct values of that column. It is sequential, in the foreground, with no progress bar and no way to cancel — the only real network risk here. Untick it if the browse looks at a large table over a slow link.
A wrong guess at the browse object does not pass quietly A BRW7 that does not exist is a compile error, not a grid that silently fails to filter.
Check boxes need no prompt If a column is an icon column (|I in the format) and its icon set is the standard ~BoxOff.ico / ~BoxOn.ico pair, the grid draws it as a check box. It draws the box and the tick rather than loading the files, so they scale with the row. A different icon set is not drawn badly — it is not drawn.
Auto-fit measures in two passes, and they are not the same pass The loaded page is already in memory, so every cell of it is measured exactly — a few dozen rows, and it is what the user is looking at. Past the page there is no queue, only the view, and walking it means EVALUATE by field name instead of WHAT by field number, because what moves is the record buffer. That is the expensive call — the totals cost ~14 µs a record for the same reason — so out there the longest text is kept by character count and only the winner is measured.

Which is an approximation, and worth naming: in a proportional font ten is are narrower than four Ws. It costs one measurement a column instead of one a cell, the page — where being wrong would show — is exact, and a column that comes out a few pixels shy is fixed by dragging it or pressing the option again.
A hidden column stays hidden Its width is zero because somebody said so, and sizing it to its content would be un-hiding it behind their back. Widths are clamped to 16 and 600 pixels, so a 4,000-character memo cannot make a 4,000-pixel column.
Which columns total is a suggestion, not a verdict The picture proposes it (@n and @e yes; @s and @d no; a check box never) and the user corrects it from the Columns dialog. It will happily offer to total a column of document numbers, because a document number is a number.

Take the typeface from SD AspectooffTypeface and size come from SDAspecto, and the two fields above are disabled. Colours are not affected.
Draw the text the way the LIST does (GDI)onA LIST is drawn by GDI and the grid by DirectWrite, and they do not render alike. See the note below.
Font weightas the name saysWhich face of the family to ask for. See the note below — this one is not cosmetic.
A family name can carry the weight inside it, and that is not a rendering difference "Roboto Medium" is a family to GDI, which resolves it to the Medium face. DirectWrite hands that same family its 400-weight member instead, which is lighter. Put a LIST and a grid side by side with the same typeface configured and the grid reads as thinner — and no amount of contrast or hinting will match them, because they are two different faces, not two renderings of the same text.

Left at as the name says, the last word of the family name — Medium, Light, SemiBold, Black, Thin — is read and that weight is asked for. Name it explicitly when the family name does not say.
GDI and DirectWrite really do render differently GDI snaps the stems to the pixel grid and adds contrast, so they look thicker. Ticked, the grid asks DirectWrite for GDI_CLASSIC hinting with ClearType and GDI's enhanced contrast. Gamma, ClearType level and subpixel order come from the machine's own settings rather than constants — they are what the user left in the ClearType panel, and overriding them would fix the weight and break the colour of the text on displays that are not RGB.
SDAspecto's typography is resolved at run time, not at generate time The grid asks the global instance — GLO_SDAspecto.FuenteNombre and .FuenteTamano — rather than copying its prompts. It has to: SDAspecto's prompts are the factory value, and its INI is read afterwards and overrides them. Reading the prompt gave a grid configured at 11 while the rest of the window ran at 9 because the INI said 9 — never failing, just uneven.

FuenteAControles is honoured, because the grid is a control: if SDAspecto has been told not to touch controls, the grid keeps its own typeface just like the LIST beside it. Empty and -1 mean “leave this alone”, so they fall back to this tab's value — worth keeping sensible even while it looks disabled.
A cell's colour beats the column's, and the column's beats the row's The BrowseBox's conditional colours and the formatter's fixed ones are honoured with nothing to configure; these eight are the ground they are applied over.

What the end user gets #

None of this needs code from you.

The heading menu

With the drop-down button switched on, every heading opens up to eleven options — Filter by value… can be left out from the prompts:

OptionWhat it does
Sort Ascending / DescendingHands the request to the browse, which sorts by its own rule.
Filter on {value}Filters by the selected row's value in that column.
Filter by value…Opens the list of distinct values in the column, to tick the ones that matter.
Find text…Asks for a string and keeps the rows that contain it. Case is ignored; in a numeric column it looks for an equal value. A tick in the dialog searches every column instead of just this one.
Clear this filterOnly that column's.
Clear all filtersEvery column's.
Columns…Show, hide, and choose which columns carry a total.
Auto-fit widthsSizes every visible column to the widest of its heading and its values, in one go.
Layouts…Save the columns you are using under a name, and bring them back later. See Column layouts.
Reset layoutBack to the design widths, and forget what was remembered.

Filters are per column and they accumulate: filtering a second column does not replace the first. They are applied through the browse object's SetFilter with an identifier of their own per column, so whatever filter you put on the BrowseBox stays intact and ABC joins them for you.

The dialogs

In Columns and Filter by value the space bar toggles the highlighted row, and there are buttons for whoever prefers to press one. Columns will not let you accept with everything hidden: a grid with no columns has nowhere to click to undo it. Find text is a single line plus the tick that widens the search to every column.

Column layouts #

One user works with columns A, B and C; another prefers A, C and D. Each saves their own under a name and brings it back.

Layouts… on the heading menu opens a small dialog: the list of saved layouts, a name, and Save / Load / Delete. It stores each column's width, which columns are visible, and which ones carry a total. Up to twenty.

It needs Remember this grid's layout between runs, which is where the storage lives, and it inherits from the global like the rest of the menu.

It invents no storage A layout is exactly what the grid already remembered between runs, written to a named section instead of the usual one. Loading copies that section over the usual one and reopens — so a loaded layout is also the one that comes back on its own next time, with no second place where the truth could differ.
No filters, and no column order Filters are not saved for the same reason they are not remembered: a filter is an expression, and one that will not parse is a run-time error at window open, before there is anything on screen to explain it. A wrong width looks odd; a wrong filter locks you out. Order is not saved because the grid does not reorder columns.

From your own code

The same two operations are routines, so an embed can drive them — the dialog calls these very routines, rather than keeping a second copy that could drift:

Grid1:SchName = 'Sales'
DO BG:SchLoad:Grid1
IF ~Grid1:SchDid                     ! nothing stored under that name

Grid1:SchName = 'Sales'
DO BG:SchSave:Grid1                  ! and it joins the list

There is also a code template — BrowseGrid - load a column layout — to drag onto an embed. It takes the grid's object name and the layout name, with a tick saying whether that name is a variable or a literal.

What the code template is for The layout that follows from who opened the window — their department, their role — which is not something the user can choose by pressing a button. Point it at a variable, name the saved layouts after the values that variable takes, and each user arrives with their own columns.

Put it on an embed that runs after the grid exists (ThisWindow.Init, after the parent call, is the natural place). Earlier there is nothing to rearrange and the call leaves quietly.

Hooks for your code #

Two situations where the grid needs to be told.

If you touch the queue directly

The grid learns the queue changed when ABC calls Reset or TakeNewSelection. A hand-written PUT(Queue:N) — which is how tagging templates tick a row — fires neither, so the cell goes on showing the old value. Tell it:

POST(BG:Refill:Grid1)      ! the equate carries the object name

That pours the queue into the grid and repaints, in memory. It is preferable to ThisWindow.Reset(1), which rereads the file.

If another template issues the refresh DAS_Tagging emits ThisWindow.Reset(1) of its own accord — there is nothing to change and nothing worth editing: the template already hooks Reset and refills the grid by itself.

If you tick or toggle by clicking a column

Those templates read PROPLIST:MouseDownRow and MouseDownField from the LIST — that is, where the user clicked on it. The grid covers the LIST, so that click never arrives and the column stops responding. Name the column number in LIST columns that also get the click and the grid sets those two properties up and posts the event.

Only the columns you name — and not out of decorative caution EVENT:Accepted on a browse LIST is also how ABC is told a record was chosen. Posting it on every click would open the edit form every time somebody touched a row.

Limits & costs #

Measured on a real application, not estimated.

What drawing costs

A complete fill — reading the queue and handing the engine every visible cell — costs under 200 µs. A frame at 60 Hz is 16,666 µs, so that is 1.2 % of a frame. With the arrow key held down at 30 repeats a second, the grid uses 0.6 % of one core.

What it costs on disk

There are three file accesses in all the generated code, and none of them is on the drawing path. Everything else works against the in-memory queue ABC has already filled: BrowseClass does exactly the I/O it did before.

What the grid does not see

  • Column setup after Init, unless you turn the re-read on.
  • The total is not recomputed when a range limit changes from another control. Sorting does not recompute it either, and that is correct: sorting does not change the set.

Diagnostics #

With one tick, the grid says what it is doing. The window title shows the column map:

BG 1>f1[@s20]w102S- 2>f2[@n3]w22i3S- 3>f4[@s60]w442S=CUE:SALDO
   | q=16 fill=30 cols=3 rowh=21 page=15 us=126 avg=143

Per column: which LIST column it came from, which queue field it reads, its picture, its width in pixels, and whether it carries an icon (i), colours (c) or a total (S=). Then how many records the queue holds, how many fills have happened, and what the last fill took in microseconds.

BrowseGrid.log is written beside the executable only when the column map changes, so the transition that matters is not buried under hundreds of identical lines. On opening, it also records what typeface each thing ended up with:

Grid4 tipografia: lista=Roboto Medium/9 ventana=Roboto Medium/9
                  grid=Roboto Medium/11 dpi=96

All three on one line because the useful question is not what size the grid is, but whether it is the same size as everything else. dpi is there because the engine builds its surface pinned at 96: at dpi=96 the numbers mean the same thing and a difference is a real difference; on a scaled display the grid comes out smaller even when both say the same size.

When a browse draws nothing that map says immediately whether the problem was the queue, the columns, or rows that did not fit — which are three different fixes.

With diagnostics off, none of this is generated.
